PLAY SPEED (patches/v4.9.11.0/play.js; phone width, 4x CPU throttling, example magus)
- Keyed redraw: renderPlay hands its page and console strings to window.amPlaySet, which keeps every block whose
  markup is unchanged (the hero and its crest, untouched sections, open folds) and compares changed blocks child by
  child, matched by tag, id and class, three levels deep; only what changed is rebuilt. Nodes later wrappers insert (the Situation strip) are not in
  the markup, so they are removed and re-inserted by those wrappers as before, never left stale. The first draw
  after a mode switch, and window.amPlayFull, use a full innerHTML redraw. Every Play tab reads the same through
  the keyed path as through a full redraw (tested).
- No layout read back mid-redraw: the console scroll position is remembered from its scroll events instead of read
  at the start of each redraw, and is restored only when the console was rebuilt; the section strip's sticky offsets
  (psecAfter) are measured in the next animation frame; the root custom properties --hdr-h, --psec-nav-h,
  --f975-top and --f975-sb are written only when they change (writing one restyles the whole page); the Build/Play
  switch's aria-pressed is written only when it changes, so its slide animation no longer measures after every
  redraw. A Play click now lays the page out once (was three times).
- Measured, same session, 4 clicks each: loading a roll 131–216 → 89–118 ms; Situation stress chip 101–155 →
  88–94 ms; Magic/Skills tab 149–287 → 93–177 ms; a redraw with nothing changed 112–152 → 70–84 ms. UI audit
  "load a roll" at 390 px (four skin/theme pairs, includes a 200 ms wait): 421–656 → 360–424 ms.
- Left for later: playSheet still rebuilds every check's string (≈30 ms of each click at 4x), and P() and XP()
  copy their defaults on every call (≈13 ms); both change long-standing behaviour and are not touched here.
